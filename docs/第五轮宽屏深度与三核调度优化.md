# 第五轮：宽屏深度模型、三核调度与延迟优化

日期：2026-11-25。已在同一台RK3588上完成代码、模型、真实相机、HDMI翻页、质量一致性和退出恢复验证。**默认相机配置采用518×294 FP16单上下文低延迟模式，另提供三上下文吞吐模式；原518×518模型保留。** 两种模式都未达到深度20FPS目标。

## 核心0繁忙的原因与处理

原深度模型的注意力计算约占原逐层采样69%，RK3588的exSDPAttention不支持多核联合，见[官方2.3.2算子手册](https://github.com/airockchip/rknn-toolkit2/blob/v2.3.2/doc/05_RKNN_Compiler_Support_Operator_List_V2.3.2.pdf)章节3.2.78。mask7允许使用三个核心，不会使所有算子自动三核并行。

本轮单独绑定掩码1、2、4验证了三个核心均可工作。原518×518模型单上下文约1.42FPS；改成三个独立上下文后，三核都繁忙，但仅约2.44FPS，内部帧龄P95约1262ms。因此不能只把核心占用拉高作为优化结果。

## 有效的计算量优化

16:9相机画面在原518×518输入中，真实RGB区域约518×291，其余是上下填充。新模型518×294仍保留同样的518×291 RGB采样，移除上下各112像素的填充。RGA硬件测试确认：新输入与旧输入中央裁剪逐像素完全相同。

Transformer网格由37×37变为37×21；包含类别token的序列长度由1370减至778，注意力分数矩阵元素数量约减至32.2%。同时减少了MLP、深度解码头和CPU Resize的工作量。原学习权重、归一化参数和FP16精度保留。位置编码插值与填充上下文发生变化，预测结果不与原模型逐元素相同。

其他配套改变：

- 最新帧槽保存NV12，选中参与推理的帧后才转换RGB；减少慢模型下大量无效颜色转换。单独ABBA测得CPU约41.2%→26.9%，该项本身没有明显FPS或延迟收益。
- 推理线程绑定本进程允许的RK3588 A76核心4–7，采集、桌面和系统调度配置保持原设置。独立ABBA模型调用约651.4→620.7ms。绑定针对本线程，不改变系统全局亲和性或频率。
- 单上下文继续mask7；三个上下文分别绑定NPU掩码1、2、4，共享有界最新帧/结果槽，统计主动替换与乱序结果。
- 保留上一轮后台保存，保存任务仍有界，慢磁盘不会不断积压显示队列。

## 实测结果

共同条件：1080p30相机采样、1080p60 HDMI、原Depth Anything V2 Small学习权重、FP16、20秒或30秒短测。低延迟方案与原方案采用ABBA各30秒，save_every=0；表内同类两轮的分位数取算术平均，不是合并样本分位数。

| 配置 | 稳态处理FPS | 内部帧龄P95 | NPU各核平均负载 | 请求时长 |
|---|---:|---:|---|---|
| 原518×518、单上下文 | 1.413 | 845.6ms | 约78% / 8% / 8% | 2×30s |
| 518×294、单上下文低延迟 | 3.554 | 366.4ms | 约76% / 12% / 12% | 2×30s |
| 518×294、双上下文 | 5.068 | 473.8ms | 约73% / 74% / 0% | 20s |
| 518×294、三上下文吞吐 | 6.006 | 542.1ms | 约67% / 67% / 68% | 20s |

低延迟模式的处理帧率约为原方案2.52倍，P95减少约56.7%；三上下文帧率约为原方案4.25倍，但帧龄高于新单上下文。核负载是整轮遥测均值，包含启动和退出。

独立NPU模型调用ABBA使用同一张相机样本、同样的A76亲和性和mask7：原模型622.08ms，新模型247.34ms，耗时减少约60.2%。真实流水线模型调用P50约272ms；独立调用和流水线条件不同，应分别理解。

单上下文请求180秒复测，save_every=20：3.542FPS、内部帧龄P95 368.4ms、最高温度48.08℃。三上下文仅完成20秒短测，尚未完成长时间稳定性验收。

## 质量与适用范围

| 检查 | 结果 |
|---|---|
| 50张验证图，板端FP16对新形状FP32 ONNX | Spearman中位数0.999942，最低0.999360 |
| 18张相机帧，板端新模型对原模型真实画面区域 | Spearman中位数0.997792，最低0.996815 |
| 18帧仿射对齐后RMSE / 原深度P95–P5范围 | 中位数2.41%，最大3.13% |
| 18帧深度梯度相关性 | 中位数0.9306，最低0.8520 |

采用预设工程门槛：50图FP16秩相关中位数≥0.99且最低≥0.98；相机秩相关中位数≥0.98且最低≥0.95；归一化RMSE中位数≤5%且最大≤10%；梯度相关中位数≥0.90且最低≥0.80。全部通过。50图检查的是FP16转换一致性；新旧形状的质量比较仅覆盖既有相机序列的18帧，不能视为多场景或米制深度精度验收，梯度相关也不等于所有物体边缘精度相同。

宽屏模式仅接受16:9输入，其他比例会报错并恢复设备。使用image/video参数时默认回到原518×518模型；也可以显式指定standard。后续应补充动态人物、近距离细物体、强光和低照度的独立场景，比较深度稳定性及边缘。

## 稳定性与未采用的路径

- CTest 4/4通过，含新增RGA矩形输入与旧方形裁剪逐像素一致性检查。
- 300ms阻塞注入后，出现一次约702ms帧龄长尾，在后续1帧内恢复到400ms以下；没有持续积压。
- 两次手动启动/停止均成功，停止约2.6秒；非16:9输入和模拟显示错误均按预期退出并恢复相机、桌面。模拟错误不代表物理HDMI拔插测试。
- YOLO回归约29.93FPS，超分回归约11.82FPS，未切换其默认模型和精度。
- 本轮启动ID始终一致，未观察到重启。此前未知原因重启未被解释，长期稳定性标记保持false，默认无开机自启。
- 关闭SDPA融合的隔离重复测试没有收益；一次与板端编译重叠的初测已标为无效，以无并发重复结果为准。
- GPU内置Resize不受当前Runtime支持；自定义GPU路径出现Runtime内布局转换内核To8未定义错误，隔离2.5.0也失败；自定义CPU Resize原型约723ms，反而变慢。均未接入默认程序。GPU别名、候选库、头文件和原型只在state实验目录，系统与项目私有运行库保持原版本。

本轮未测整板瓦特功耗。内部帧龄从appsink取样到HDMI翻页，不含曝光、取样前等待及屏幕响应；不宣称光学150ms达标，也不是mpp_decode_bench的4K60编解码验收。

## 操作与代码

```bash
cd "/userdata/av_dev/advanced algorithms"
# 默认相机低延迟；此专用脚本关闭图像/张量保存
bash depth_anything_v2/start_low_latency.sh
bash depth_anything_v2/status.sh
bash depth_anything_v2/stop.sh
# 三核并发吞吐模式
bash depth_anything_v2/start_throughput.sh
bash depth_anything_v2/stop.sh
# 原518×518参考方案
bash depth_anything_v2/start.sh --depth-profile standard --capture-convert eager --inference-cpus auto --workers 1
```

默认start.sh读取recommended.json，使用相机camera-rect、单上下文、selected颜色转换和A76亲和性；默认保存间隔仍为300。两个专用启动脚本设置save_every=0，可追加`--save-every 300`覆盖。

源码主要改动在common/main.cpp、core.hpp、camera.cpp和preprocess.cpp；tools/control.py选择模型、参数并监督恢复。新模型为depth_anything_v2/models/fp16-camera-518x294.rknn，原模型fp16.rknn保留。转换/验证工具为tools/probe_depth_aspect.py、build_depth_camera.py、check_depth_camera.py，转换依赖原有固定Docker环境和原始权重。

新宽屏模型使用Git LFS，Git克隆时应拉取实际模型文件：

```bash
git lfs install --local
git lfs pull --include="depth_anything_v2/models/fp16-camera-518x294.rknn"
python3 tools/preflight.py
```

完整本地记录：state/npu-candidates；持久验证收据：docs/round5-validation.json。Windows和板端都保留源码与模型；GitHub发布状态以提交历史为准。测试后算法预览保持停止，桌面恢复。
